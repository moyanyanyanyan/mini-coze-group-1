**表结构要点**

```
Conversation  id, userId, agentId?, title(默认「新对话」), createdAt, updatedAt
              @@index([userId, updatedAt])
Message       id, conversationId, role, status, seq, content, createdAt
              @@index([conversationId, seq])
```

- `role` 取值 `user` / `assistant`；`status` 取值 `pending` / `running` / `completed` / `failed` / `cancelled`
- 两张表都用 String 存枚举，不用 Prisma enum（避免多人改 schema 冲突）
- `agentId` 是可选字段：**知识库归属的粒度由它决定，需与陈弘毅、管逸恬对齐**

## 二、接口方式（REST，`/api` 前缀，全部需要登录）

**鉴权**：HttpOnly Cookie `access_token`（7 天，SameSite=Lax）。前端请求一律 `credentials: 'include'`，**不传 Authorization header**。公开 API 入口走 API Key，是 D 模块内容，不在本表。

| 方法与路径 | 请求体 | 成功响应 | 说明 |
| --- | --- | --- | --- |
| `POST /api/conversations` | `{ agentId?: string }` | `201 { id, title, agentId, createdAt, updatedAt }` | 不传 agentId 也能建，先空着 |
| `GET /api/conversations` | — | `200 ConversationSummary[]` | 按 `updatedAt` 倒序，只返回自己的 |
| `GET /api/conversations/:id/messages` | — | `200 ChatMessage[]` | 按 `seq` 正序 |
| `POST /api/conversations/:id/messages` | `{ content: string }` | 见第三节 | 发消息主路径 |
| `DELETE /api/conversations/:id` | — | `204` | 级联删消息 |

**共享类型（写在 `packages/shared`）**

```ts
export interface ConversationSummary {
  id: string;
  title: string;
  agentId: string | null;
  createdAt: string;   // ISO
  updatedAt: string;   // ISO
}

export interface ChatMessage {
  id: string;
  conversationId: string;
  role: 'user' | 'assistant';
  status: 'pending' | 'running' | 'completed' | 'failed' | 'cancelled';
  seq: number;
  content: string;
  createdAt: string;
}
```

时间字段统一 **ISO 字符串**，不传 Date 对象。

**错误码**

| 状态码 | 内部码 | 场景 |
| --- | --- | --- |
| 401 | `TOKEN_INVALID` | Cookie 无效 / 用户已删除 |
| 404 | `CONVERSATION_NOT_FOUND` | 不存在**或不是自己的**（统一 404，防探测） |
| 409 | `CONVERSATION_BUSY` | 同一会话上一轮还在生成 |
| 503 | `RUNTIME_UNAVAILABLE` | Runtime 401 / 5xx / 连不上 |

## 三、发消息的两种形态

### 阶段 1（B 模块，Runtime 未接入）

```http
POST /api/conversations/:id/messages
{"content": "你好"}
```
```json
200 {"userMessage": {...}, "assistantMessage": {...}}
```
助手回复是**固定占位**（`这是一条占位回复，Runtime 接入后替换`）。一次写两条消息，`seq` 自增。

### 阶段 2（C 模块，Runtime 接入后）

同一个接口，响应头变成 `Content-Type: text/event-stream`，返回 SSE 流。**前端不能用 `EventSource`**（它只发 GET、不能 POST），用 `fetch` + `ReadableStream` 逐块解析。

| 事件 | data 载荷 | 来源 |
| --- | --- | --- |
| `run.started` | `{ assistantMessageId }` | Runtime |
| `knowledge.result` | `{ status, chunks:[{content, score, citation}] }` | **管逸恬的 KB** |
| `message.delta` | `{ content }` | Runtime |
| `tool.started` / `tool.completed` | `{ toolCallId, toolName, ... }` | 朱曾亨插件 |
| `run.completed` | `{ content, citations, finishReason, usage }` | Runtime（唯一成功终止） |
| `run.failed` | `{ code, message, retryable }` | Runtime（唯一失败终止） |

- 每个事件带扁平信封 `{ runId, conversationId, seq, timestamp, type, data }`
- 心跳 15s 发 `: ping`，**不占 seq**
- 落库铁律：Runtime 不写库；NestJS 校验「全部 delta 拼接 == `run.completed.data.content`」后一次性落库，**落库成功才转发 `run.completed`**，失败发 `PERSISTENCE_FAILED`

## 四、与知识库模块的衔接（给管逸恬）

1. **不需要她提供 NestJS 接口**。KB 检索在 Runtime(8000) 内部，NestJS 只把 `agentConfig` 快照（含 `knowledgeBaseIds`）随请求传进去，检索结果以 `knowledge.result` 事件回吐，NestJS 原样转发给前端并在落库时存 `citations`。
2. **她缺少的「聊天侧入口」不是她那边的问题**，是我 B 模块的 B4。在她拿到页面之前，可以用第四节末尾的 curl 直接打 Runtime 自测。
3. **需三方对齐的点**：`knowledgeBaseIds` 绑定在 Agent 上（陈弘毅）还是直接绑会话。我这边默认：发消息带 `agentId` → NestJS 读 Agent 配置快照 → 取出 `knowledgeBaseIds` → 传给 Runtime。若她的实现是按 `conversationId` 或 `userId` 取 KB，**现在就要改**。

## 五、可直接自测的 curl 模板（不依赖前端）

```bash
# 1) 登录拿 Cookie
curl -i -c cookies.txt -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"12345678"}'

# 2) 建会话
curl -b cookies.txt -X POST http://localhost:3000/api/conversations \
  -H "Content-Type: application/json" -d '{"agentId":"<AGENT_ID>"}'

# 3) 发消息（阶段1 返回 JSON，阶段2 加 -N 流式输出）
curl -N -b cookies.txt -X POST http://localhost:3000/api/conversations/<CONV_ID>/messages \
  -H "Content-Type: application/json" -d '{"content":"你好"}'
```
