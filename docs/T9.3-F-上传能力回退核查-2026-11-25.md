# T9.3-F 补充：PDF/IMAGE/DOCX/PPTX 上传能力回退核查

日期：2026-11-25
范围：`mini-coze-group-1-pdf` 当前 checkout

## 结论

**是，当前 checkout 不具备 PDF / IMAGE / DOCX / PPTX 上传能力。**

这是相对历史分支 `feature/gyt/addParsingType` 的能力缺失，不是 T9.2（MD/HTML 适配）或 T9.3-F（枚举补齐）删除代码导致的。当前分支 HEAD `91113b1` 是历史分支的祖先，历史分支上后续 11 个提交尚未合并进来。

T9.3-F 只补了数据库枚举和前端类型，**没有恢复上传、解析和 OCR/Office 处理链路**。

## 代码层证据

### 1. 上传类型入口只允许 4 种

`apps/backend/src/modules/knowledge/documents/document-content.ts`：

```ts
export type FileDocumentSourceType = 'TXT' | 'JSON' | 'MARKDOWN' | 'HTML';
```

`.pdf`、`.png/.jpg/.jpeg`、`.docx`、`.pptx` 均直接抛出 `UNSUPPORTED_FILE`。

### 2. 解析分发只支持 4 种

`parse-document.ts` 的 `ParsedSourceType` 只有：

```text
TEXT / TXT / JSON / MARKDOWN / HTML
```

PDF/IMAGE/DOCX/PPTX 即使绕过上传入口，也会在 `EXTRACTING` 阶段失败。

### 3. 全局上传限额未按类型区分

当前 `FileInterceptor` 统一使用 `MAX_DOCUMENT_BYTES`（1 MB），因此真实图片在进入类型校验前就可能返回 413。历史实现按类型区分：

- TXT/JSON：1 MiB
- PDF：64 MiB
- DOCX/PPTX：32 MiB
- PNG/JPG/JPEG：10 MiB

### 4. 前端文件选择器未包含这些扩展名

当前 `accept`：

```text
.txt,.json,.md,.markdown,.html,.htm
```

历史实现：

```text
.txt,.json,.pdf,.docx,.pptx,.png,.jpg,.jpeg
```

## 建议

优先合并历史分支 `feature/gyt/addParsingType` 的 11 个提交，再与当前 T9.2 的 `NormalizedDocument` / `chunk-source` 链路做适配。直接在当前分支重新实现会重复 OCR、OOXML、资源限制和来源映射逻辑，风险更高。

在恢复前，不应把 T9.3-F 的枚举补齐视为“上传能力已恢复”。
