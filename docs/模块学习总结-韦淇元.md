# MiniCoze 模块学习总结：登录、用户、会话与流式对话

> 面向第一次读这个项目的人。本文以当前分支 `feature/weiqiyuan/login-backend` 的代码为准，配合分支提交历史和已有协作文档整理。重点是图片中的 A、B、C 模块；D（发布与公开 API）只说明边界，不把它当成已完成。
>
> 先记住一个区分：图片是计划和验收清单，文档可能是较早的设计版本，代码才代表当前分支实际上做了什么。遇到不一致时，本文会指出来。

## 1. 一句话看懂项目

这是一个让用户创建智能体、配置它，再和它聊天的 Web 应用。你负责的主线可以概括为：

```text
注册/登录 -> 后端认出当前用户 -> 用户创建或找回会话 -> 发消息
    -> 后端保存消息并取得智能体配置 -> Python Runtime 调模型
    -> Runtime 持续发回 SSE 事件 -> 后端保存最终结果 -> 页面显示回复
```

几个基础名词：

| 名词 | 用大白话理解 | 在项目里 |
|---|---|---|
| 前端 / Web | 用户看到并点击的页面 | `apps/web`，React + TypeScript |
| 后端 / Backend | 接请求、做权限检查、读写数据库、协调服务 | `apps/backend`，NestJS + TypeScript |
| 数据库 | 长期保存用户、Agent、会话、消息等资料 | PostgreSQL，由 Prisma 访问 |
| Runtime | 真正执行智能体：组织提示词、取知识、调用模型和工具 | `apps/agent`，Python + FastAPI |
| API | 程序之间约定好的请求地址、参数和返回格式 | Web 调 NestJS；NestJS 调 Runtime |
| JWT | 后端签发的登录凭证。像一张有期限的通行证 | Cookie 中的 `access_token`，也兼容 Bearer 请求头 |
| SSE | 服务器不等任务全部做完，而是边做边连续发送事件 | 聊天回答可以逐段出现 |
| 契约 | 两个模块对字段和行为达成的共同约定 | `packages/shared` 和 `docs/契约-*` |

## 2. 整个程序如何启动和分工

项目不是一个程序包办所有事，而是三个进程各司其职：

```text
浏览器 React
  |  HTTP / SSE，携带登录 Cookie
  v
NestJS Backend
  |-- Prisma ----------------------> PostgreSQL
  |-- HTTP + 内部服务令牌 ----------> Python Runtime
                                       |-- 知识库检索（需要时）
                                       |-- 插件调用（需要时）
                                       `-- 大语言模型
```

浏览器不直接连数据库，也不直接访问 Python Runtime。这样做有两个好处：用户身份、会话归属和数据库写入集中在后端；Runtime 不必知道浏览器登录细节，只接收后端整理好的请求。

开发时通常分别启动数据库、Backend、Runtime、Web。`docker-compose.yml` 提供数据库配置；根目录 `package.json` 和各 app 的 `package.json` 定义脚本。具体环境变量看 `.env.example`：例如 `DATABASE_URL`、`JWT_SECRET`、`AGENT_SERVICE_URL`、`INTERNAL_SERVICE_TOKEN`。`.env` 是本机秘密配置，不应提交。

## 3. A 模块：认证与用户（先确定“你是谁”）

### 3.1 用户资料和登录凭证不是一回事

数据库 `User` 保存用户的长期资料：用户 ID、邮箱、昵称、头像、密码哈希、Google 账号 ID 等。`CurrentUser` 是后端交给业务模块使用的“安全版用户资料”，只含 `id/email/displayName/avatarUrl`，不含 `passwordHash`。它定义在 `packages/shared/src/index.ts`，前后端用同一套字段。

因此，其他业务模块不应该拿邮箱判断数据归谁，而应统一用 `CurrentUser.id`。例如新建会话时，后端从认证结果取得 `user.id`，写入 `Conversation.userId`。调用者不能在请求体里随意指定所有者 ID。

### 3.2 注册是怎么走的

```text
用户填写邮箱、密码、昵称
 -> Web 调 POST /api/auth/register
 -> NestJS ValidationPipe 按 RegisterDto 校验
 -> AuthService 查邮箱是否已注册
 -> UsersService 用 bcryptjs 把密码变成不可直接还原的哈希
 -> Prisma 创建 User 记录
 -> AuthService 签发 JWT
 -> Controller 把 JWT 放进 HttpOnly Cookie，并返回安全版 user
```

密码哈希不是“加密后存起来再解密”，而是单向校验值。登录时，`bcrypt.compare` 会比较用户输入和数据库哈希；数据库泄露时，攻击者不会直接看到原密码。重复邮箱返回 `EMAIL_ALREADY_REGISTERED`。

### 3.3 登录后，后端如何认出每个请求

当前实现的浏览器凭证方案是 HttpOnly Cookie：登录成功后，浏览器保存 `access_token` Cookie；`HttpOnly` 的意思是普通前端 JavaScript 不能直接读取它，减少 XSS 窃取凭证的机会。Web 请求统一设置 `credentials: 'include'`，NestJS 的 CORS 也启用了 credentials。

每次访问受保护的接口，Passport 的 `AuthGuard('jwt')` 会先拦住请求。`JwtStrategy` 从 Cookie（优先）或 `Authorization: Bearer ...`（兼容）提取 JWT，验证签名和有效期，再用 JWT 的 `sub` 查数据库中的用户。查到后，把经过 `toCurrentUser()` 脱敏的对象放到 `request.user`。Controller 用 `@CurrentUser()` 把它取出来。

```text
请求 -> AuthGuard -> JwtStrategy 验签/查用户 -> request.user
                                           -> Controller 的 @CurrentUser()
```

`GET /api/auth/me` 是最容易理解的验收接口：有有效凭证就返回当前用户；没凭证或过期就返回 401。退出登录调用 `POST /api/auth/logout`，后端清掉 Cookie。JWT 本身是无状态凭证，因此这个 MVP 的退出是让浏览器丢弃凭证，不是服务器把 JWT 加入黑名单。

### 3.4 Google 登录

当前分支已经有 Google OAuth 全链路，而不是图片早期标注的“可选未开始”。流程是浏览器跳到 `/api/auth/google`，后端生成随机 `state` 并放进短期 HttpOnly Cookie；Google 授权后回调 `/api/auth/google/callback`，后端检查 `state` 防止伪造回调，再用 OAuth provider 换令牌、读取 Google 资料。只有 Google 声明邮箱已验证时才接受。随后按 Google ID 找用户、给已有同邮箱账号绑定 Google ID，或创建新用户，最后仍签发本项目自己的 JWT Cookie。

注意：Google 令牌只用于和 Google 交互；访问本项目 API 时，项目验证的是自己的 `access_token`。

### 3.5 错误和验证

DTO（例如 `RegisterDto`）描述请求体允许有什么字段、格式和长度。全局 `ValidationPipe` 会校验输入并移除未声明字段。`HttpExceptionFilter` 把异常转换成响应；认证接口提供 `statusCode/code/message/path/timestamp`，例如 `INVALID_CREDENTIALS`。前端应按稳定的 `code` 判断情况，不要靠中文提示文字判断。

重要代码：`apps/backend/src/modules/auth/`、`apps/backend/src/modules/users/`、`apps/backend/src/common/`、`apps/backend/test/auth.e2e-spec.ts`、`apps/web/src/features/auth/`。

## 4. B 模块：会话与历史（聊天消息放在哪里）

### 4.1 会话和消息的关系

可以把 `Conversation` 想成聊天文件夹，把 `Message` 想成文件夹里的每一句话。一个会话属于一个用户、关联一个 Agent；一个会话包含多条消息。`Message.seq` 是会话内的顺序号，`role` 表示 `user` 或 `assistant`，`status` 表示完成、生成中、失败或取消。

数据库的核心关系：

```text
User 1 ---- 多 Conversation 1 ---- 多 Message
                    |
                    `---- 一个 Agent（当前代码允许 agentId 为空）
```

`Conversation.userId` 是访问隔离的关键。读取、删除或发消息前，后端都需要把会话 ID 和当前 `user.id` 一起查；当前代码把不存在和不属于自己的会话都作为 404 返回，避免通过错误差异探测别人的会话。

### 4.2 会话相关接口

| 接口 | 用途 |
|---|---|
| `POST /api/conversations` | 建一个会话，校验 Agent 属于当前用户 |
| `GET /api/conversations` | 列当前用户的会话，最近更新的排前面 |
| `GET /api/conversations/:id/messages` | 先校验会话归属，再按 `seq` 正序读取消息 |
| `DELETE /api/conversations/:id` | 只删除当前用户自己的会话，消息通过数据库级联删除 |
| `POST /api/conversations/:id/messages/stream` | 聊天页真正使用的 SSE 发送接口 |
| `POST /api/conversations/:id/messages` | 非流式的旧/备用接口 |

前端并不是一进入“新对话”就创建空会话，而是等用户发第一条消息时才创建。首条消息会截取前 20 个字符作为标题；历史列表只拿摘要，点开后再单独读取消息正文，避免列表请求携带所有历史文本。

重要代码：`apps/backend/src/modules/conversations/`、`apps/backend/prisma/schema.prisma`、`apps/web/src/features/agent-chat/components/ConversationList.tsx`。

## 5. C 模块：流式对话（把问题送给 AI，再把回答送回来）

这是最值得沿着代码读一遍的部分。网页的流式路径不是“浏览器直接问模型”，而是经过后端的 ChatService。当前代码的实际入口是 `/api/conversations/:id/messages/stream`；图片和早期契约里的 `/api/agents/:agentId/chat/stream` 是旧计划路径，不是当前聊天页在用的路径。

你特别说明 C 模块是 AI 帮你完成的，所以学习重点不应是背每一行代码，而是先能回答三件事：请求从哪里进来、数据经过哪些中间对象、什么时候保存数据库。下面的流程图和部件表就是这三个问题的答案；读代码时可以从 `AgentChatPage.handleSend` 一路跳到 `chat-api.streamMessage`，再跳到后端的 `ChatController -> ChatService -> RuntimeClientService`。

### 5.1 一次聊天的完整工作流程

```text
1. 用户在 MessageComposer 输入并发送
2. AgentChatPage 必要时创建 Conversation，先在屏幕乐观显示用户消息和空的 AI 气泡
3. 浏览器 fetch 流式接口，带 HttpOnly Cookie
4. ChatController 验证 JWT、检查会话属于当前用户、检查 Agent 可用
5. ChatService 检查同一会话是否已有生成任务
6. ChatService 在数据库事务里保存用户消息和 assistant pending 占位消息
7. ChatService 读取之前已完成的问答对，排除本轮消息，最多 20 条
8. 后端组装 RuntimeRequest：用户 ID、会话 ID、Agent 配置、历史、当前问题
9. RuntimeClientService 请求 Python Runtime 的 /internal/runtime/stream
10. Runtime 调知识库/插件（如已绑定），再调用模型，发出 SSE 事件
11. NestJS 解析每个 SSE 帧，将事件转给浏览器；delta 内容逐段显示
12. Runtime 发 run.completed 或 run.failed；后端保存最终状态和文本后再转发终态
13. 浏览器收尾：完成、失败或用户停止；释放发送状态
```

步骤 6 很重要：消息先落库，生成中断时才有一条 assistant 记录可保存已生成的部分内容。历史也不能把本轮刚写入的用户消息重复塞进去，所以代码用消息 ID 排除本轮，再按完整的 user/assistant 对筛选历史。

### 5.2 SSE 是什么

普通 HTTP 更像打电话问一个问题，对方想好完整答案后一次性说完。SSE 更像电话保持接通，对方每想到一小段就说一段。这里每个事件的网络文本大致是：

```text
event: message.delta
data: {"runId":"...","conversationId":"...","seq":3,"type":"message.delta","data":{"content":"你好"}}

```

事件按序号递增。最常见的几种：`run.started` 表示开始；`message.delta` 是新生成的一段文字；`knowledge.result` 是引用来源；`tool.started/tool.completed` 是插件过程；`run.completed` 是成功结束；`run.failed` 是失败结束。`run.completed` 和 `run.failed` 是终态，同一轮最多有一个。

底层网络可以把一个事件拆成多块，也可能把中文字符的 UTF-8 字节拆开。后端和前端都用 `TextDecoder(...).decode(bytes, {stream:true})`，并用 buffer 等完整的 `\n\n` 事件边界到齐后再解析。因此 `fetch + ReadableStream` 是流式聊天的实现方式；浏览器原生 `EventSource` 不适合这里，因为需要 POST 请求体和 Cookie/鉴权处理。

### 5.3 谁负责哪一段

| 部件 | 职责 | 入口代码 |
|---|---|---|
| `AgentChatPage` | 加载 Agent/会话/历史，管理 UI 状态，停止生成，乐观更新 | `apps/web/src/features/agent-chat/AgentChatPage.tsx` |
| `chat-api.ts` | 发起浏览器流式请求、解码 SSE、把事件分发给页面 | `apps/web/src/features/agent-chat/api/chat-api.ts` |
| `ChatController` | HTTP 入口、JWT 和会话/Agent 检查，设置 SSE 响应头、转发事件 | `apps/backend/src/chat/chat.controller.ts` |
| `ChatService` | 业务大脑：并发闸门、落库、组 history 和 Runtime 请求、处理终态 | `apps/backend/src/chat/chat.service.ts` |
| `RuntimeClientService` | 调 Python 服务、解析 Runtime 的 SSE | `apps/backend/src/chat/runtime-client.service.ts` |
| Python `RuntimeService` | 知识检索/插件/模型调用并产出统一事件 | `apps/agent/app/runtime/service.py`、`apps/agent/app/api/runtime.py` |

### 5.4 停止、失败和并发

停止按钮调用浏览器 `AbortController.abort()`。浏览器请求断开后，Controller 的 `close` 事件触发后端 AbortController，再一路把 signal 传给 Runtime 的 fetch。ChatService 捕获中断，把已生成文本保留在消息记录里并标记 `cancelled`。用户主动停止不应该显示成普通错误。

同一会话再发一次消息可能导致两个模型任务抢同一段上下文，所以后端 `ChatService` 用 `busy` 集合限制同一会话同时只能跑一轮，重复请求返回 409 `CONVERSATION_BUSY`。注意这是进程内集合；如果未来 Backend 多实例部署，需要换成数据库/Redis 等跨实例协调机制，当前内存锁不能让多个服务器互相看见。

成功终态的文本由 Runtime 的 `run.completed.data.content` 提供，后端保存后才把成功事件送给浏览器。这样避免页面以为成功、刷新后数据库却没有内容。Runtime 断线或返回失败则按失败/取消状态保存 partial 内容。

### 5.5 Agent 配置如何影响回答

ChatService 不自己猜模型参数，而是让 `AgentsService.getAgentConfig()` 检查 Agent 所有权，再通过 mapper 整理出 Runtime 要的快照：系统提示、模型、温度、最大 token 数、启用的知识库 ID、插件 ID。Runtime 根据这些配置调用相应能力。

这里的温度可以粗略理解为回答变化程度；最大 token 数是模型输出长度上限；系统提示是 Agent 的角色和规则；绑定知识库提供参考资料，绑定插件提供可执行工具。模型具体生成发生在 Python Runtime，不在 NestJS ChatService。

### 5.6 D 模块的边界（当前分支还没有完成）

D 的目标是发布 Agent，让外部程序用 API Key 调用它。它涉及发布状态/配置版本、Key 的生成和哈希存储、公开 API 鉴权、公开流式端点和 SDK。当前分支的 `PublishingModule` 是空模块，代码树也没有可用的 `public-api` 后端实现；所以不要把图片或其他历史提交中的设计/提交记录当成当前分支 D 已可运行。图片说 D 未实现，与当前代码状态吻合。

设计上，D 应该复用 C 的 ChatService，这样网页和公开 API 才不会各自维护一套消息持久化与 Runtime 逻辑。但只有当当前分支真正有公开入口和 API Key 鉴权实现时，这条路径才算落地。
