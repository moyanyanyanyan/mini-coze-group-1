# 对话上下文压缩改造

日期：2026-11-28。本文方案已实现，并完成真实模型验收。

## 问题与方案

原先智能体编辑器可选 0、5、10、20、50、100 轮，但后端实际最多携带 10 轮；接近预算时 Runtime 成对丢弃最早历史。“几轮可用”只是窗口位置计数，容易被误读为剩余聊天次数，实际没有会话摘要压缩。

改造为：

1. 聊天页只保留上下文用量环和悬浮明细，移除记忆展开条、轮数倒计数和冗长来源说明。用量优先读取服务端预览，不再把单次模型调用的 Token 当成整个上下文的占用。
2. 智能体配置表示“近期原文轮数”，最多 100 轮；0 表示不带入历史。超出近期窗口或接近 Token 预算时，较早原文通过当前配置的实际模型生成摘要。
3. 摘要增量更新并存入会话，原始消息不删除。摘要作为普通参考数据参与上下文，不提升为系统指令。运行管理仍可核对当前摘要与近期原文。

## 实际链路

```mermaid
flowchart LR
  Send[网页聊天 / 对外 API] --> Auth[验证用户、会话、智能体及附件]
  Auth --> History[筛选已完成的完整问答]
  History --> Split[按原文轮数和 Token 预算划分]
  Split --> Old[旧摘要 + 新增较早原文]
  Old --> Compress[内部鉴权接口 context/compress]
  Compress --> Model[智能体当前配置的实际模型]
  Model --> Save[归属和处理位置校验后保存新摘要]
  Save --> Context[系统提示词 + 历史摘要 + 近期原文 + 新问题]
  Context --> Reply[正常模型 / 工具 / 检索执行]
```

摘要保存在 `Conversation.contextSummary`，处理到的助手消息 ID 保存在 `contextSummaryThrough`。这两个字段均可空，已有会话无需回填；首次达到阈值后自动生成。

较长旧消息先拆成 Unicode 安全的小段，再按输入预算分批压缩。每批合并上批摘要，全部成功后才推进会话处理位置。保存使用当前用户与旧处理位置作条件，避免并发覆盖更新。取消请求会终止后续压缩调用。

压缩失败明确返回 `CONTEXT_COMPRESSION_FAILED`，保留旧摘要、处理位置和原文；不会把未完整生成的摘要保存为成功。本轮新消息在压缩成功后才入库。聊天前端保留输入草稿和未绑定附件，方便重试。

读取记忆预览不会执行模型或写入摘要。有待压缩历史时只标记等待下次发送处理。压缩实际用量另外写入 `OperationTelemetry(kind=context_compression)`，不伪造为主回答的用量，也不混入现有仅统计主运行的 Token 汇总。

摘要属于有损语义压缩，原文始终保留以供核对；运行时仍保留预算硬校验，当前问题、附件或工具本身过大时会明确拒绝。

## 验证结果

- 后端完整测试：63 个测试文件、529 个用例通过。
- UI 完整测试：23 个测试文件、89 个用例通过；前端完整测试通过，另新增压缩失败时保留草稿/附件的回归验证。
- Agent 完整测试：189 个用例通过。
- 前后端构建、类型检查通过。
- 真实模型连续两轮压缩验收：摘要保留 `TeyvatCode`、`TypeScript`、不能使用 Python、人物索引排序等约束；后续真实回答正确引用这些内容。16 条原始消息均保留。
- 两次真实压缩分别报告 506 和 324 Token；临时验收会话和智能体已清理。
- 浏览器检查确认聊天页三个旧展示已移除，用量明细仍可悬浮或键盘聚焦访问。
